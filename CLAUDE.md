# AI Safety Resources — project guide

A curated, static collection of AI safety & alignment resources (books, papers,
films, TV, documentaries, podcasts, courses, YouTube, websites) served from
`public/`, with a small dependency-free Node build step. The mobile app in
`mobile/` has its own `CLAUDE.md` — read that one when working there.

## The one invariant that matters

`public/resources.js` is the **only hand-edited data file**. Everything else is
generated by `node scripts/build.mjs` and must never be edited by hand:

- `data/resources.json`, `data/search-index.json`
- `public/resource-tags.js`
- the injected panes, Start-here cards, and JSON-LD inside `public/index.html`
- `public/<category>/index.html`, `public/topics/**`, `public/paths/**`
- `public/sitemap.xml`

After changing `public/resources.js` or `scripts/lib/resources.mjs`, always run
`npm run build` and commit the regenerated files. CI (`npm run check` in
`.github/workflows/build.yml`) fails the PR if committed output is out of sync.

## Commands

```bash
npm run build        # validate + regenerate all derived files
npm run check        # validate only (CI gate), no writes
npm run guardrails   # dead-link checker (also runs on PRs + weekly cron)
```

There are no npm dependencies and no test framework; the build pipeline is
deliberately zero-dependency. Do not add packages to the root project.

## Editing the dataset

Each entry in `public/resources.js`: required `Name`, `Link` (http/https),
`Category` (see `VALID_CATEGORIES` in `scripts/lib/resources.mjs`). Optional:
`Author`, `Summary`, `Year` (1800–2100), `page_count`, `Minutes`/`MinutesPer`,
`Level` (`VALID_LEVELS`), `Image`, `IncludeTopics`/`ExcludeTopics` (must be
known tags from `TOPIC_TAGS`). `Category: "books"` is split into fiction vs.
non-fiction via the fiction-title list in `scripts/lib/resources.mjs`. The same
`Link` may be cross-listed in two tracks but never duplicated within one.
Validation runs at build time and fails loudly — trust it.

Curated lists live in code, in `scripts/lib/resources.mjs`: tracks, topic tags
and topic pages, learning paths (`PATHS`), and the Start-here picks. Path and
Start-here steps are resolved against the dataset **by exact `Name`** at build
time, so renaming a resource requires updating those references (the build
fails on a mismatch). Bump `DATASET_UPDATED` there when the dataset or page
templates change meaningfully.

## Front end

`public/script.js` is a single ~5,000-line vanilla-JS file with no framework
and no bundler. It is the part of the codebase most at risk of quality decay:
keep changes small and localized, match existing patterns, and prefer deleting
or reusing code over adding parallel implementations. Server-rendered cards in
generated HTML must not contain a `<div>` (the pane-injection regex depends on
it — see `ssrPaneMarkup` in `scripts/build.mjs`).

`public/entry-meta.js` is the single source of truth for the card metadata
pills (difficulty level + time-to-consume labels). It is hand-edited,
dependency-free, and DOM-free, and is consumed by **both** sides: the browser
loads it as a classic script before `script.js` (which reads
`window.ENTRY_META`), and the build evaluates it in a vm sandbox
(`loadEntryMeta` in `scripts/lib/resources.mjs`). Edit pill rules there and
only there — never re-implement them in `script.js` or the build lib, and
after editing run `npm run build` since the labels are baked into generated
pages and data exports.

`functions/` are Cloudflare Pages Functions (suggestion/contact endpoint,
optional accounts). The site must keep working without them: no-JS fallback,
`mailto:` fallback, localStorage-only reading list by default.

## Scope discipline

The product is the **curation**, not the software. Simplicity is the moat.

- Prefer improving the dataset, summaries, tags, and learning paths over
  adding interactive features.
- New user-facing features need an explicit maintainer request — do not add
  them opportunistically while fixing something else.
- Every feature must degrade gracefully (static HTML fallback, optional APIs).
- When asked to "improve" something without a spec, propose a short plan
  before writing code; ask for the design intent rather than guessing it.
